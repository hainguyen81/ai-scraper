### 🔹 Phase 1: User Management, Authentication, and Authorization
- **Original Objective**: Implement User Management, Authentication, and Authorization.  
- **Gap Analysis**: Original phase lacked explicit tenant provisioning, role‑based access control (RBAC), MFA enforcement, audit‑log schema, and a defined user lifecycle state machine. No messaging contract for user events.  
- **Augmented Architecture & Solutions**:  
  - **Data Models/Schema** (MongoDB collections):  
    - **Tenants** (`tenant_id`, `name`, `status`, `subscription_tier`, `created_at`)  
    - **Users** (`user_id`, `tenant_id`, `email`, `password_hash`, `role`, `mfa_enabled`, `created_at`, `last_login`)  
    - **Sessions** (`session_id`, `user_id`, `tenant_id`, `jwt_token`, `refresh_token`, `issued_at`, `expires_at`, `revoked`)  
    - **Roles** (`role_id`, `tenant_id`, `name`, `permissions`)  
  - **API & Event Contracts** (Express routes, request/response payloads):  
    - `POST /auth/signup` – `{email, password, companyName}` → `201 Created` with `user_id`  
    - `POST /auth/login` – `{email, password, mfaCode}` → `200 OK` with `access_token`, `refresh_token`  
    - `POST /auth/logout` – `Authorization: Bearer <token>` → `200 OK` (revokes session)  
    - `GET /users/me` – `Authorization: Bearer <token>` → user profile  
    - **Event Bus**: RabbitMQ exchange `user_events` (direct), queue `user_event_queue`, routing keys `user.created`, `user.verified`, `user.login`, `user.logout`. DLQ: `user_event_dlq`.  
  - **State‑Machine Lifecycle** (User):  
    - **UNVERIFIED** → `email_verification` trigger → **ACTIVE**  
    - **ACTIVE** → `login` trigger → **ACTIVE** (session renewal)  
    - **ACTIVE** → `deactivate` trigger → **SUSPENDED**  
    - **SUSPENDED** → `reactivate` trigger → **ACTIVE**  
    - **ACTIVE** → `delete_account` trigger → **DEACTIVATED** (soft‑delete)  
  - **Security Controls**: Argon2id password hashing (salt 16 B, mem 64 MiB, iter 3), JWT RS256 (24 h expiry), MFA via TOTP/SMS, TLS 1.3, AES‑256‑GCM for token encryption, OWASP Top‑10 mitigations, audit logs written to `AuditLogs` collection (see Phase 4).  
  - **Observability**: Prometheus counters (`auth_attempts_total`, `auth_success_total`), latency histograms (`auth_request_duration_seconds`), Grafana panels for sign‑up/login rates, ELK pipeline for auth‑related logs.

### 🔹 Phase 2: Autonomous Pricing Engine, Inventory Sync, and Advertising Scheduler
- **Original Objective**: Develop Autonomous Pricing Engine, Inventory Sync, and Advertising Scheduler.  
- **Gap Analysis**: Original phase missing concrete micro‑service definitions, AI pricing engine contract, inventory webhook schema with optimistic locking, advertising scheduler UI/API, durable message‑queue for failures, and observability.  
- **Augmented Architecture & Solutions**:  
  - **Data Models/Schema** (per‑tenant MongoDB databases):  
    - **Products** (`product_id`, `tenant_id`, `sku`, `name`, `price` (Decimal), `stock_quantity` (Int), `version` (Int), `status` (ACTIVE/OUT_OF_STOCK/DISCONTINUED), `last_updated`)  
    - **PricingRules** (`rule_id`, `tenant_id`, `rule_name`, `conditions` (JSON), `actions` (JSON), `enabled`, `created_at`)  
    - **PricingSuggestions** (`suggestion_id`, `tenant_id`, `product_id`, `suggested_price`, `confidence_score`, `generated_at`, `status` (PENDING/ACCEPTED/REJECTED))  
    - **InventoryEvents** (`event_id`, `tenant_id`, `product_id`, `quantity_change`, `new_quantity`, `version`, `event_type` (IN/OUT/ADJUST), `timestamp`, `source`)  
    - **Campaigns** (`campaign_id`, `tenant_id`, `name`, `ad_platform` (INSTAGRAM/FACEBOOK/GOOGLE_SHOPPING), `status` (DRAFT/SCHEDULED/RUNNING/COMPLETED/CANCELLED), `schedule_start`, `schedule_end`, `budget`, `created_by`, `created_at`)  
    - **CreativeAssets** (`asset_id`, `tenant_id`, `campaign_id`, `file_name`, `file_path`, `file_size` (BigInt), `mime_type`, `uploaded_at`)  
  - **API & Event Contracts**:  
    - **Pricing Engine Service** (`./sources/backend/pricing-engine/`):  
      - `POST /pricing/suggest` – `{product_id, competitor_prices[], demand_score}` → `202 Accepted` with `suggestion_id`  
      - `GET /pricing/suggestions/{suggestion_id}` – polling endpoint  
      - **Event**: `pricing.suggest` (routing key) published to RabbitMQ exchange `pricing_events`.  
    - **Inventory Sync Service** (`./sources/backend/inventory-sync/`):  
      - `POST /webhooks/inventory` – `{product_id, quantity, version, timestamp}` → `200 OK` or `409 Conflict` (optimistic lock)  
      - `GET /products/{product_id}/stock` – cached response (Redis TTL 30 s)  
      - **Event**: `inventory.delta` (routing key) to exchange `inventory_events`.  
    - **Advertising Scheduler Service** (`./sources/backend/ad-scheduler/`):  
      - `POST /campaigns` – `{name, ad_platform, schedule_start, schedule_end, budget, creative_ids[]}` → `201 Created` with `campaign_id`  
      - `PUT /campaigns/{campaign_id}/status` – `{status}` (internal state transitions)  
      - `GET /campaigns/{campaign_id}` – campaign details  
      - **Event**: `scheduler.create` and `scheduler.execute` routed via exchange `ad_scheduler_events`.  
  - **Messaging Topology** (RabbitMQ):  
    - Exchanges: `pricing_events` (direct), `inventory_events` (direct), `ad_scheduler_events` (direct).  
    - Queues: `pricing_queue`, `inventory_queue`, `scheduler_queue`.  
    - Routing Keys: `pricing.suggest`, `inventory.delta`, `scheduler.create`, `scheduler.execute`.  
    - DLQ Setup: each queue has a corresponding DLQ (`pricing_dlq`, `inventory_dlq`, `scheduler_dlq`) with `x-dead-letter-exchange` pointing to the primary exchange.  
    - Consumer retries: exponential back‑off (base 1 s, max 30 s), max 5 attempts before DLQ.  
  - **State‑Machine Lifecycles**:  
    - **PricingSuggestion**: `REQUESTED` → `PROCESSING` (AI model) → `COMPLETED`/`FAILED`.  
    - **InventoryEvent**: `RECEIVED` → `VALIDATED` → `APPLIED` (update `Products`) → `CONFLICT` (if version mismatch).  
    - **Campaign**: `DRAFT` → `SCHEDULED` → `RUNNING` (ad‑platform API call) → `COMPLETED`/`CANCELLED`.  
  - **Security Controls**: JWT tenant isolation, row‑level security on all collections, AES‑256‑KMS at‑rest, TLS 1.3, OWASP mitigations, input validation, rate limiting at API gateway.  
  - **Observability**: Prometheus metrics (`pricing_suggestion_duration_seconds`, `inventory_webhook_latency_seconds`, `campaign_execution_success_total`), Grafana dashboards, ELK logs for pricing and inventory events, Jaeger traces for cross‑service flows.

## 🛡️ 3. Enterprise Compliance, High Availability & Disaster Recovery
- **Security Boundaries**:  
  - API Gateway enforces mutual TLS, JWT validation, rate limiting (1000 req/min per tenant).  
  - Service mesh (Istio) implements mTLS, traffic policies, and request tracing.  
  - Each microservice runs with least‑privilege IAM roles; database access via MongoDB Atlas with tenant‑specific user credentials.  
  - Encryption‑in‑transit: TLS 1.3 with forward secrecy; encryption‑at‑rest: AES‑256‑KMS.  
  - OWASP Top‑10 mitigations embedded in code (input validation, output encoding, SQL/NoSQL injection prevention, XSS, etc.).  
- **Asynchronous Failover Logic**:  
  - All critical async operations (pricing suggestions, inventory updates, ad‑platform calls) are published to RabbitMQ with persistent delivery.  
  - Consumer processes messages with exponential back‑off (base 1 s, max 30 s). After 5 unsuccessful attempts, message is routed to DLQ.  
  - DLQ consumers log failures to `AuditLogs`, trigger alerts via SNS/PagerDuty, and provide manual retry UI.  
  - Circuit breaker pattern (Hystrix) for external dependencies; after 5 consecutive failures, circuit opens for 30 s, returning fallback responses (stale data).  
- **High Availability**:  
  - Multi‑AZ Kubernetes clusters with replica sets; HPA based on CPU/memory/latency.  
  - Load balancer (Application Load Balancer) distributes traffic; health checks every 30 s.  
  - Redis cluster for caching; data replication across AZs.  
- **Disaster Recovery**:  
  - Active‑active across two AWS regions; cross‑region replication for MongoDB (Atlas Global Clusters).  
  - Automated daily snapshots and point‑in‑time recovery (PITR) retained 30 days.  
  - RTO ≤ 4 h, RPO ≤ 5 min.  
  - Failover orchestrated via Route 53 latency‑based routing; DNS TTL set to 60 s for rapid propagation.  
- **Compliance & Auditing**:  
  - All audit events (user actions, price changes, inventory updates, campaign creations) are appended to immutable `AuditLogs` collection with SHA‑256 hash chaining.  
  - Log retention policy: 365 days; encrypted storage; access limited to compliance role.  
  - Quarterly penetration testing, vulnerability scanning, and SOC 2 Type II audits.
