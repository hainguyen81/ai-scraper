## 1. Introduction  

### 1.1 Purpose  
This SRS documents the functional and non‑functional requirements for the Enterprise Data‑Integration Platform (EDIP). It aligns the system architecture with the Idea, Blueprint, and audit findings, ensuring that all data flows, naming conventions, security controls, technology choices, and ownership responsibilities are explicitly defined.

### 1.2 Scope  
EDIP is a modular, service‑oriented platform that ingests, transforms, and routes data between internal business systems (Modules A, B, and C) and external partners. The platform must support real‑time and batch processing, provide a RESTful API surface, and enforce enterprise security policies.

## 2. Overall Description  

### 2.1 Product Perspective  
EDIP is a standalone micro‑service ecosystem that will be deployed on the company’s Kubernetes cluster. It interfaces with legacy ERP systems, external partner APIs, and internal analytics dashboards.

### 2.2 Product Functions  
1. **Ingest** data from multiple sources (REST, FTP, Kafka).  
2. **Validate** incoming payloads against schema definitions.  
3. **Transform** data using configurable mapping rules.  
4. **Route** transformed data to target systems.  
5. **Persist** data in a relational database (PostgreSQL).  
6. **Expose** a versioned REST API for CRUD operations.  
7. **Audit** all transactions and security events.  

### 2.3 User Classes and Characteristics  
| User Class | Role | Characteristics |
|------------|------|-----------------|
| System Administrator | Maintains deployment, monitors health | Technical, high‑privilege |
| Data Engineer | Configures ingestion/transform pipelines | Domain expert, moderate technical |
| Business Analyst | Consumes data via API | Non‑technical, requires clear docs |
| Security Officer | Oversees compliance | Regulatory knowledge |

### 2.4 Operating Environment  
- **Hardware**: Kubernetes cluster on AWS EKS (≥ 3 nodes).  
- **Software**: Docker 20.10, Kubernetes 1.28, PostgreSQL 15, Java 17, Spring Boot 3.0.  
- **Network**: TLS 1.3, VPC isolation, IAM roles.  

### 2.5 Design and Implementation Constraints  
- Must comply with GDPR and ISO 27001.  
- All APIs must be documented in OpenAPI 3.0.  
- Deployment must use immutable containers.  

### 2.6 Assumptions and Dependencies  
- External partner APIs will provide OAuth2 tokens.  
- Data schema definitions will be supplied by the Data Governance team.  
- The audit recommendations will be implemented before production release.

## 3. System Features  

### 3.1 Feature 1 – Module A: Data Ingestion Service  
| Requirement ID | Description | Acceptance Criteria |
|----------------|-------------|---------------------|
| FR‑A‑01 | Accept JSON payloads over HTTPS | Payload size ≤ 10 MB, 200 OK on success |
| FR‑A‑02 | Support FTP ingestion | File checksum verified, 200 OK on success |
| FR‑A‑03 | Consume Kafka streams | Offset committed, no data loss |

### 3.2 Feature 2 – Module B: Data Transformation Service  
| Requirement ID | Description | Acceptance Criteria |
|----------------|-------------|---------------------|
| FR‑B‑01 | Apply mapping rules defined in YAML | Transformed record matches expected schema |
| FR‑B‑02 | Handle data type conversions | No runtime errors for invalid types |
| FR‑B‑03 | Log transformation steps | Log entry per record with timestamp |

### 3.3 Feature 3 – Module C: Data Storage & Retrieval Service  
| Requirement ID | Description | Acceptance Criteria |
|----------------|-------------|---------------------|
| FR‑C‑01 | Persist transformed data in PostgreSQL | Data integrity verified via checksum |
| FR‑C‑02 | Provide CRUD API endpoints | 200 OK on successful operations |
| FR‑C‑03 | Support pagination and filtering | Response time ≤ 200 ms for 10 k rows |

### 3.4 Data Flow Between Module A and Module B  
**Issue 1** from the audit identified a missing data contract.  
**Resolution:**  
- **Data Contract**: JSON schema `ingest_to_transform_v1.json` (see Appendix A).  
- **Flow**:  
  1. Module A validates payload against `ingest_schema_v1.json`.  
  2. Module A publishes validated record to Kafka topic `ingest_to_transform`.  
  3. Module B consumes from `ingest_to_transform`, validates against `ingest_to_transform_v1.json`, applies mapping, and publishes to `transform_to_store`.  
  4. Module C consumes from `transform_to_store` and persists.  

All data contracts are versioned and stored in the Git repository `edip/contracts`.

## 4. External Interface Requirements  

### 4.1 User Interfaces  
- **Admin Dashboard**: Web UI built with React, secured via SSO.  
- **API Console**: Swagger UI for developers.  

### 4.2 Hardware Interfaces  
- None (cloud‑native).  

### 4.3 Software Interfaces  

#### 4.3.1 API Naming Convention  
**Issue 2** from the audit highlighted inconsistent naming.  
**Standard:**  
- Base path: `/api/v1/`  
- Resource names: plural, lower‑case, hyphenated (e.g., `/api/v1/records`).  
- Action verbs: `GET`, `POST`, `PUT`, `DELETE`.  
- Query parameters: snake_case.  

All endpoints must be documented in OpenAPI 3.0 and validated against the schema `api_spec_v1.yaml`.

#### 4.3.2 Third‑Party Integrations  
- **Partner API**: OAuth2, scopes `read:data`, `write:data`.  
- **Kafka**: TLS‑encrypted, SASL/PLAIN authentication.  

### 4.4 Communication Interfaces  
- **REST**: HTTPS, TLS 1.3, JSON payloads.  
- **Kafka**: TLS, SASL/PLAIN.  
- **FTP**: FTPS, explicit TLS.

## 6. Security Requirements  

### 6.1 Authentication  
- All APIs require OAuth2 bearer tokens.  
- Tokens issued by the company’s Identity Provider (IdP).  

### 6.2 Authorization  
- Role‑based access control (RBAC) enforced at API gateway.  
- Minimum privilege principle for service accounts.  

### 6.3 Data Protection  
- TLS 1.3 for all network traffic.  
- Data at rest encrypted using AWS KMS.  
- Sensitive fields masked in logs.  

### 6.4 Audit Logging  
- Centralized ELK stack.  
- Log retention: 90 days.  
- Log entries include user ID, action, timestamp, and resource ID.  

### 6.5 Penetration Testing  
- Conducted by the Security Team on 2026‑09‑15.  
- Findings addressed per audit recommendation.  

### 6.6 Compliance  
- GDPR: Data subject rights handled via API endpoints.  
- ISO 27001: Controls mapped in the Security Policy document.
