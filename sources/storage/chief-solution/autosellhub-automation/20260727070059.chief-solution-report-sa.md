## 1. Executive Summary  

This blueprint formalises the architectural design of the Enterprise Data‑Integration Platform (EDIP) in alignment with the SRS (v1.2) and the audit findings (Audit Report 1.0). It resolves identified gaps in data contracts, naming conventions, deprecated technology, and ownership clarity. The blueprint is intended for architects, developers, security, and operations teams and serves as the definitive reference for implementation, testing, and future evolution.

---

## 2. Architecture Overview  

EDIP is a **service‑oriented, Kubernetes‑native micro‑service ecosystem** that ingests, validates, transforms, routes, and persists data across internal business modules (A, B, C) and external partners. The platform supports **real‑time** (Kafka, REST) and **batch** (FTP, scheduled jobs) processing, exposes a **RESTful API surface** for CRUD operations, and enforces enterprise security policies (OAuth2, TLS 1.3, RBAC, ISO 27001, GDPR).

Key architectural principles:

| Principle | Description |
|-----------|-------------|
| **Modularity** | Each core function is isolated in a dedicated micro‑service (Module A, B, C). |
| **Loose Coupling** | Services communicate via well‑defined contracts (JSON schemas) over Kafka or REST. |
| **Immutable Deployments** | Containers are built from source, signed, and deployed as immutable artifacts. |
| **Observability** | Centralised metrics (Prometheus), logs (ELK), and traces (OpenTelemetry). |
| **Security‑First** | End‑to‑end encryption, least‑privilege service accounts, and audit logging. |
| **Scalability** | Horizontal scaling via Kubernetes HPA, Kafka partitions, and stateless services. |
| **Compliance** | GDPR‑ready data handling, ISO 27001 controls, and audit‑ready logging. |

## 5. Data Flow Diagrams  

### 5.1 DFD Level 0 – System Overview  

```
[External Partner] --> [API Gateway] --> [Module A] --> [Kafka] --> [Module B] --> [Kafka] --> [Module C] --> [PostgreSQL]
```

### 5.2 DFD Level 1 – Detailed Flow  

1. **Ingestion**  
   - REST: Partner sends JSON → API Gateway → Module A (POST /ingest).  
   - FTP: Partner uploads file → FTPS → Module A (FTP listener).  
   - Kafka: Partner publishes to `partner_ingest` → Module A (Kafka consumer).  

2. **Validation**  
   - Module A validates against `ingest_schema_v1.json`.  
   - On success, publishes to `ingest_to_transform`.  

3. **Transformation**  
   - Module B consumes `ingest_to_transform`.  
   - Validates against `ingest_to_transform_v1.json`.  
   - Applies mapping rules from `edip/mapping`.  
   - Publishes to `transform_to_store`.  

4. **Storage**  
   - Module C consumes `transform_to_store`.  
   - Persists to PostgreSQL.  
   - Exposes CRUD via API Gateway.  

5. **Audit & Monitoring**  
   - All services emit logs to ELK.  
   - Metrics to Prometheus.  
   - Traces to Jaeger.

## 6. Deployment Architecture  

| Layer | Technology | Configuration | Notes |
|-------|------------|---------------|-------|
| **Infrastructure** | AWS EKS (v1.28) | 3 worker nodes (m5.large), VPC isolation, IAM roles | Auto‑scaling enabled |
| **Container Runtime** | Docker 20.10 | Immutable images signed with Notary | |
| **Service Mesh** | Istio 1.18 | Mutual TLS, traffic routing | Optional – can be replaced by Linkerd |
| **API Gateway** | Kong 3.0 | OAuth2 plugin, rate‑limit, TLS termination | Deployed as a Kubernetes Deployment |
| **Message Broker** | Apache Kafka 3.3 | TLS‑encrypted, SASL/PLAIN, 3 brokers | Hosted on EKS via Strimzi |
| **Database** | PostgreSQL 15 | StatefulSet, encrypted volumes via AWS KMS | Backups via Velero |
| **Observability** | ELK (Elasticsearch 8.5, Logstash 8.5, Kibana 8.5) | Fluentd sidecar for logs | |
| **Metrics** | Prometheus 2.47, Grafana 9.5 | ServiceMonitor CRDs | |
| **Tracing** | OpenTelemetry Collector, Jaeger 1.45 | Exporter to Jaeger | |
| **CI/CD** | GitHub Actions, Helm 3 | Build, test, push to ECR, Helm upgrade | |
| **Secrets Management** | AWS Secrets Manager | OAuth client secrets, DB credentials | |

**Deployment Flow**  
1. Commit code → GitHub Actions triggers build.  
2. Docker image built, signed, pushed to ECR.  
3. Helm chart packaged, versioned, deployed to EKS.  
4. Kubernetes controller reconciles desired state.  
5. Health checks (liveness/readiness) ensure service availability.

## 7. Security Architecture  

| Domain | Controls | Implementation |
|--------|----------|----------------|
| **Authentication** | OAuth2 bearer tokens | IdP (AWS Cognito) → API Gateway → Services |
| **Authorization** | RBAC at API Gateway + service‑level ACLs | Kong ACL plugin, Spring Security |
| **Transport Security** | TLS 1.3 | API Gateway TLS termination, internal mTLS (Istio) |
| **Data at Rest** | AES‑256 via AWS KMS | PostgreSQL encrypted tablespaces |
| **Data in Transit** | TLS, SASL/PLAIN for Kafka | Strimzi TLS config |
| **Logging** | Centralised ELK, audit logs | Logstash pipeline, retention 90 days |
| **Secrets** | AWS Secrets Manager | Kubernetes secrets via External Secrets |
| **Penetration Testing** | Quarterly scans | OWASP ZAP, Burp Suite |
| **Compliance** | GDPR, ISO 27001 | Data subject rights API, ISO controls mapping |
| **Incident Response** | SIEM integration | ELK alerts, PagerDuty |

## 9. Naming & Contract Conventions  

| Area | Convention | Reference |
|------|------------|-----------|
| **API Base Path** | `/api/v1/` | SRS 4.3.1 |
| **Resource Names** | Plural, lower‑case, hyphenated (e.g., `/api/v1/records`) | SRS 4.3.1 |
| **Action Verbs** | HTTP methods only (GET, POST, PUT, DELETE) | SRS 4.3.1 |
| **Query Parameters** | snake_case (e.g., `page_size`) | SRS 4.3.1 |
| **Data Contracts** | JSON Schema, versioned (`*_v1.json`) | Audit Finding 1 |
| **Contract Repository** | `edip/contracts` in Git | SRS 3.4 |
| **Mapping Rules** | YAML, versioned (`*_v1.yaml`) | SRS 3.2 |
| **Service Names** | `module-a`, `module-b`, `module-c` | SRS 2.1 |
| **Docker Images** | `company/edip-module-a:1.2.0` | CI/CD policy |
| **Helm Charts** | `edip-module-a`, `edip-module-b`, `edip-module-c` | Helm repo |
