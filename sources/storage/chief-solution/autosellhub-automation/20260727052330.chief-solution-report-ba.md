# Prompt for Business Analyst – Chief Solution Architect (CSA) Role

## Context
You are an Enterprise Business Analyst tasked with authoring and overhauling software requirements specifications (SRS) that are **absolutely aligned** with product ideas. Your work must be precise, comprehensive, and follow a strict set of conventions.

## Instructions
1. **Read and understand the product idea** – focus on the *business objectives*, *user expectations*, and *technical constraints*.
2. **Identify all functional and non‑functional requirements** – break them down into clear, testable statements.
3. **Structure the SRS** using the following sections (in this exact order):
   1. Introduction and Overview
   2. Existing System / Current State
   3. Proposed System / Desired State
   4. Detailed Functional Requirements
   5. Detailed Non‑Functional Requirements
   6. User Stories / Use Cases (if applicable)
   7. Assumptions, Constraints, and Dependencies
   8. Acceptance Criteria
   9. Glossary
4. **Use consistent formatting** – headings (#, ##, ###), bullet points, and tables where appropriate.
5. **Validate the SRS** against the product idea and ensure that every requirement is **traceable** to a business objective.
6. **Incorporate feedback** from stakeholders and iterate until the SRS is **complete** and **clear**.

## Review Signals
- **Clarity** – Is the language unambiguous and easy to understand?
- **Completeness** – Are all necessary requirements covered?
- **Consistency** – Do the sections flow logically and reference each other correctly?
- **Testability** – Can each requirement be verified with concrete acceptance criteria?
- **Traceability** – Is each requirement linked to a business objective or user need?
- **Prioritization** – Are high‑priority items clearly marked (e.g., using **[HIGH]**, **[MED]**, **[LOW]**)?
- **Version Control** – Is the document versioned and change‑controlled?
- **Stakeholder Sign‑off** – Has the document been reviewed and approved by key stakeholders?

## Output Format
- The final SRS must be a **single Markdown file** named `srs.md`.
- Include a **header** with the document title, version, date, and author.
- Append a **change log** at the end of the document.
- Ensure the document is **well‑structured**, **readable**, and **professional**.

# Software Requirements Specification (SRS)
Version: 1.0
Date: 2023-10-01
Author: AI Business Analyst

## 1. Introduction and Overview
The **E‑Commerce Platform** is a cloud‑native marketplace that enables multiple vendors to sell products online. The system aims to provide a seamless shopping experience for end‑customers, robust inventory and sales tools for vendors, and comprehensive administrative controls for platform managers.

### 1.1 Purpose
- Provide a scalable, secure, and user‑friendly environment for online commerce.
- Support high‑traffic periods (e.g., flash sales) without degradation of service.
- Integrate with third‑party payment processors and CRM tools.

### 1.2 Business Objectives
- Increase overall sales revenue by **20%** within the first year.
- Reduce order processing time by **30%** through automation.
- Improve customer satisfaction scores by **15%**.
- Ensure full compliance with **PCI DSS** security standards.

### 1.3 Scope
- Core functionalities include product browsing, cart management, order processing, inventory control, and user administration.
- The system will be built using modern web technologies and deployed on AWS.

### 1.4 Definitions
- **Vendor** – Registered seller who lists and manages products.
- **End‑Customer** – Anonymous or registered user who purchases products.
- **Administrator** – Platform super‑user with full system privileges.

## 2. Existing System / Current State
The current solution relies on a **legacy monolithic application** hosted on a private data center. Key limitations include:
- Manual inventory updates causing stock discrepancies.
- Slow checkout process due to synchronous database calls.
- Limited scalability during promotional events.
- Inconsistent user experience across devices.

## 3. Proposed System / Desired State
The new system will be **microservices‑based**, containerized, and hosted on AWS. It will leverage:
- **API‑first** design for seamless integration.
- **Real‑time inventory** synchronization using event‑driven architecture.
- **Load balancing** and **auto‑scaling** to handle traffic spikes.
- **OAuth 2.0** for secure authentication and authorization.

## 4. Detailed Functional Requirements
| # | Requirement | Priority | Description |
|---|-------------|----------|-------------|
| FR‑1 | **[HIGH]** Allow customers to search products by keyword, category, and price range. | **[HIGH]** | The system shall index all products and provide a searchable interface that returns relevant results within 2 seconds. |
| FR‑2 | **[HIGH]** Enable customers to add/remove items from a shopping cart. | **[HIGH]** | Cart operations must be atomic and reflect real‑time inventory availability. |
| FR‑3 | **[HIGH]** Process orders securely using a PCI‑DSS compliant payment gateway. | **[HIGH]** | The system shall integrate with Stripe (or similar) to capture payment details, tokenize them, and confirm transactions. |
| FR‑4 | **[MED]** Allow vendors to manage inventory levels (add, update, delete). | **[MED]** | Inventory updates shall trigger events that propagate to the search index and order module. |
| FR‑5 | **[MED]** Generate sales reports for vendors (total sales, units sold, revenue). | **[MED]** | Reports shall be downloadable in CSV format and accessible via vendor dashboard. |
| FR‑6 | **[LOW]** Provide administrator tools for user role management and system monitoring. | **[LOW]** | Admins can assign roles, view audit logs, and monitor system health metrics. |

### 4.1 Traceability to Business Objectives
- **FR‑1** supports **Objective 3** (customer satisfaction) by improving search relevance.
- **FR‑2** supports **Objective 2** (order processing speed) by streamlining cart operations.
- **FR‑3** supports **Objective 4** (security compliance) by using PCI‑DSS compliant payments.
- **FR‑4** supports **Objective 1** (sales revenue) by ensuring accurate inventory to avoid stockouts.
- **FR‑5** supports **Objective 1** (sales revenue) by providing data for vendor optimization.
- **FR‑6** supports **Objective 2** (processing time) by enabling efficient system oversight.

## 5. Detailed Non‑Functional Requirements
| # | Requirement | Description |
|---|-------------|-------------|
| NFR‑1 | **Performance** – The system shall respond to user‑initiated queries within **2 seconds** (95th percentile). |
| NFR‑2 | **Security** – All data in transit must be encrypted using **TLS 1.3**; sensitive data at rest must be encrypted using **AES‑256**. |
| NFR‑3 | **Usability** – The user interface shall be responsive and accessible, supporting **WCAG 2.1 AA** standards. |
| NFR‑4 | **Maintainability** – The codebase shall follow **DRY** principles, with unit test coverage ≥ **80%**. |
| NFR‑5 | **Scalability** – The platform shall automatically scale to support **10,000 concurrent users** during peak events. |
| NFR‑6 | **Availability** – The system shall achieve **99.9% uptime** (excluding planned maintenance). |

## 6. User Stories / Use Cases
### 6.1 User Story – End‑Customer
- **Given** a customer is on the product listing page,
- **When** they enter “wireless headphones” in the search bar and apply a price filter,
- **Then** they see a list of relevant products with price, rating, and availability, and can add any item to the cart.

### 6.2 User Story – Vendor
- **Given** a vendor logs into the dashboard,
- **When** they update the stock level of a product from 5 to 0,
- **Then** the inventory system immediately reflects the change, and the product is no longer purchasable.

### 6.3 User Story – Administrator
- **Given** an administrator accesses the admin panel,
- **When** they assign the “Support” role to a new user,
- **Then** the user can view support tickets but cannot modify system settings.

## 7. Assumptions, Constraints, and Dependencies
- **Assumption A1** – The organization has an existing **AWS account** with appropriate IAM permissions.
- **Assumption A2** – The payment processor (Stripe) is already configured for the merchant account.
- **Constraint C1** – The solution must comply with **PCI DSS** standards for handling payment data.
- **Constraint C2** – The system must operate within a **GDPR‑compliant** data handling framework.
- **Dependency D1** – Integration with the **CRM** system (e.g., Salesforce) for customer data synchronization.
- **Dependency D2** – Third‑party **shipping API** (e.g., USPS) for real‑time rate calculations.

## 8. Acceptance Criteria
| Functional Requirement | Acceptance Criteria |
|------------------------|---------------------|
| **FR‑1** – Search functionality | - User can enter a keyword and receive results within 2 seconds. <br> - Results include product name, price, and rating. |
| **FR‑2** – Cart management | - Adding an item updates the cart total instantly. <br> - Removing an item clears the corresponding line item. |
| **FR‑3** – Payment processing | - Payment token is generated by the payment gateway. <br> - Transaction status is recorded and visible to the customer. |
| **FR‑4** – Inventory management | - Inventory update triggers a real‑time event to the search index. <br> - Stock level is reflected immediately on the product page. |
| **FR‑5** – Sales reporting | - Vendor can download a CSV report of sales data. <br> - Report includes total sales, units sold, and revenue. |
| **FR‑6** – Admin tools | - Administrator can assign roles and view audit logs. <br> - Role‑based access controls are enforced. |

| **CI/CD** | Continuous Integration / Continuous Deployment pipeline for automated testing and release. |
| **JWT** | JSON Web Token used for stateless authentication. |

| **OAuth 2.0** | Authorization framework that enables applications to obtain limited access to user accounts. |
