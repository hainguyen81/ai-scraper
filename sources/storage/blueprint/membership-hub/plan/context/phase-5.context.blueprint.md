# PHASE 5 CONTEXT BLUEPRINT: membership-hub

## 1 . Phase Operational Scope & Objectives
This phase focuses on deploying the membership-hub application to a GKE cluster, configuring ingress routing rules, and performing a comprehensive security audit. It encompasses container image creation, pushing to a container registry, provisioning a GKE cluster with workload identity and network policies, deploying Kubernetes manifests (cluster, deployment, services, ingress), applying security policies (PodSecurityStandards, IAM), and executing static code analysis and vulnerability scans on critical Java security configuration to ensure OWASP compliance (e.g., parameterized queries, input validation, authentication). The goal is to achieve a production‑ready, multi‑tenant, secure, and externally accessible deployment with full observability and audit trails.

## 2. Allowed Technical Scope & Directory Boundaries (Files, paths, and endpoints)
All artifacts for this phase must reside under `./sources/` and follow the topology rules:

- **Backend assets** (Docker, K8s, Java configs):
  - `./sources/backend/Dockerfile` – container definition.
  - `./sources/backend/docker-build.sh` – build & push script.
  - `./sources/backend/k8s/cluster.yaml` – GKE cluster definition.
  - `./sources/backend/k8s/deployment.yaml` – backend pod deployment.
  - `./sources/backend/k8s/service.yaml` – backend service.
  - `./sources/backend/k8s/ingress.yaml` – ingress routing.
  - `./sources/backend/k8s/helm-chart/values.yaml` – Helm values for GKE.
  - `./sources/backend/src/main/java/org/nlh4j/saas/membershiphub/security/SecurityConfig.java` – Java security configuration.
  - `./sources/backend/src/test/java/org/nlh4j/saas/membershiphub/security/SecurityConfigTest.java` – unit test for security config.
- **Frontend assets** (optional for this phase):
  - `./sources/frontend/` – may contain static assets, but not directly used in Phase 5.
- **Scripts & tooling**:
  - `./sources/backend/scripts/` – deployment helper scripts.
  - `./sources/docs/` – deployment documentation (generated by doc tasks if needed).

All paths must be absolute to the workspace root and prefixed with `./sources/`. Java source files must reside under the corporate package `org.nlh4j.saas.membershiphub` and follow the deterministic subdirectory layout.

## 3. Dedicated Sub-Agent Functional Directives (Specific tasks for coder, tester, reviewer, doc, docker, GCP, GKE)
- **docker Agent**: Responsible for creating a hardened multi‑stage Dockerfile, integrating Trivy vulnerability scanning, building the image, tagging with Git commit SHA, and pushing to Google Artifact Registry (`us-central1-docker.pkg.dev/<project>/membership-hub/backend:${GIT_COMMIT}`). Also manages the `docker-build.sh` script that orchestrates these steps and embeds OWASP A01‑A09 mitigations (e.g., parameterized queries via Hibernate, input validation, secure defaults).
- **GKE Agent**: Provisions a GKE cluster (`membership-hub-prod`) with VPC‑native mode, enables Workload Identity, applies Network Policies, enforces PodSecurityStandards (baseline), configures IAM service accounts, creates node pools, and installs the ingress‑controller (GCP Cloud Load Balancer). Applies the manifests (`cluster.yaml`, `deployment.yaml`, `service.yaml`, `ingress.yaml`) and Helm chart (`values.yaml`) to deploy the backend and expose it externally.
- **reviewer Agent**: Performs static code analysis on `SecurityConfig.java` and its unit test to verify OWASP compliance (e.g., proper password encoding, parameterized queries, CORS configuration, CSRF protection, secure headers). Runs Trivy on the built Docker image and validates that no high‑severity vulnerabilities remain. Generates a compliance report.
- **doc Agent** (if invoked): Compiles deployment runbooks, architecture diagrams (`./sources/docs/deployment-architecture.puml`), and operational procedures into `./sources/docs/phase5-deployment-guide.md`.
- **coder Agent** (if additional backend tweaks are required): May adjust application properties (`application.yml`) to inject tenant‑id scopes, AES‑256 encryption for PII, and other security parameters.
- **tester Agent** (if integration tests are needed): Executes integration tests that verify end‑to‑end functionality (e.g., health checks, tenant isolation) using the `INTEGRATION_SCOPE` token.

## 4. Phase Definition of Done (DoD)
- Docker image built, scanned (Trivy), and pushed to Artifact Registry with immutable tags.
- GKE cluster created with workload identity, network policies, and PodSecurityStandards applied.
- Backend deployment and ingress configured, services reachable, and readiness/liveness probes healthy.
- Security audit completed: `SecurityConfig.java` passes static analysis, all OWASP A‑type checks satisfied, no high‑severity vulnerabilities in the container image.
