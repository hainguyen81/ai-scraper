## 📊 1. System Overview & Scope

- **System Purpose**: AutoSellHub is a no‑code, AI‑driven automation platform that enables small e‑commerce shop owners to centrally manage product pricing, real‑time inventory, and multi‑channel advertising (Instagram, Facebook, Google Shopping) without writing code. The system reduces manual effort, improves price competitiveness, prevents stockouts, and accelerates ad campaign deployment to increase sales within days.

- **Core Scope Boundaries**:  

  **IN‑SCOPE**  
  - User registration, authentication (JWT + MFA), password policy, role‑based access control per tenant.  
  - No‑code UI builder for ad campaign creation (drag‑and‑drop, component library, validation).  
  - AI pricing engine with configurable rules, competitor monitoring, demand elasticity.  
  - Real‑time inventory synchronization across sales channels and internal catalog.  
  - Multi‑channel ad scheduler with OAuth2 integration to Instagram, Facebook, Google Shopping APIs.  
  - Multi‑tenant architecture with schema isolation, resource quotas, tenant‑specific RBAC.  
  - CI/CD pipelines, Docker containerization, Kubernetes orchestration, automated testing.  
  - Monitoring (Prometheus/Grafana), alerting, immutable audit logging, GDPR‑compliant data handling.  

  **OUT‑OF‑SCOPE**  
  - Full ERP or advanced CRM modules.  
  - Third‑party logistics (shipping, fulfillment) integration.  
  - B2B wholesale pricing or complex discount structures beyond rule‑based AI.  
  - Manual order processing or inventory reconciliation beyond automated sync.  
  - Custom code development beyond the no‑code builder.  

## ⚙️ 2. Functional Requirements & Technical Specifications

### 🔹 Module: User Management

- **FR-1.0: User Registration & Initial Tenant Creation**  
  - **Description**: New shop owners submit email, username, and password. System validates email uniqueness, enforces password policy, sends verification link, creates a tenant record and initial owner role.  
  - **Metrics/Thresholds**: Registration latency < 2 s, password hash using Argon2id (64 MiB memory, 3 iterations), email verification link expires after 48 h, tenant creation < 5 s.  
  - **Exception Flow**: Duplicate email → HTTP 409 with “Email already registered”. Weak password → HTTP 400 with list of policy violations. Email send failure → retry up to 3× with exponential backoff; after failure user must request resend.

- **FR-1.1: Authentication with MFA**  
  - **Description**: Users supply username/password then a time‑based one‑time password (TOTP). Valid credentials and MFA token produce a signed JWT (RS256) with scopes reflecting tenant roles.  
  - **Metrics/Thresholds**: Auth latency < 1 s, MFA verification < 500 ms, JWT access token expiry 15 min, refresh token expiry 24 h, token revocation stored in Redis for immediate invalidation.  
  - **Exception Flow**: Invalid credentials → HTTP 401. MFA failure >3 attempts → account locked 15 min, notification sent. Revoked token → HTTP 401 on subsequent request.

- **FR-1.2: Password Policy & Management**  
  - **Description**: Enforce minimum length 12 chars, upper/lower/digit/special, no reuse of last 5 passwords, expiration 90 days. Users can change password or request reset via email link.  
  - **Metrics/Thresholds**: Password hash Argon2id (64 MiB, 3 iter), password history 5 entries, change operation < 1 s, reset email delivery < 5 s.  
  - **Exception Flow**: Password reuse → HTTP 400 with “Password already used”. Expired reset token → HTTP 400 with “Link expired; request new one”.

- **FR-1.3: Role‑Based Access Control (RBAC) per Tenant**  
  - **Description**: Define roles Owner, Admin, Editor, Viewer. Permissions are attached to roles (e.g., Owner: full CRUD, Admin: manage users, Editor: manage products/pricing, Viewer: read‑only). Role assignments are stored in tenant‑scoped database.  
  - **Metrics/Thresholds**: Role assignment latency < 1 s, permission check overhead < 5 ms per request, max 5 roles per tenant.  
  - **Exception Flow**: Unauthorized action → HTTP 403 with audit log entry. Role assignment exceeding quota → HTTP 409.

### 🔹 Module: No‑Code UI Builder (Ad Scheduler)

- **FR-2.0: Drag‑and‑Drop Campaign Builder**  
  - **Description**: UI builder presents a component library (Image Upload, Text Overlay, Schedule Picker, Channel Selector). Users assemble components into a campaign canvas, validate inputs, and save.  
  - **Metrics/Thresholds**: Save operation < 2 s, component library version control per tenant, max 10 components per campaign, UI state persistence via local storage.  
  - **Exception Flow**: Invalid image format (non‑JPEG/PNG) → HTTP 400 with “Unsupported format”. Schedule conflict (overlapping time slots) → HTTP 409 with conflict details. Save failure (DB error) → retry 3× with backoff; after failure user notified.

- **FR-2.1: Multi‑Channel Integration (Instagram, Facebook, Google Shopping)**  
  - **Description**: Builder exports campaign JSON which is pushed via secure HTTPS to each platform’s API using OAuth2 tokens stored encrypted. Scheduler triggers publishing at defined timestamps.  
  - **Metrics/Thresholds**: API call latency < 200 ms per platform, rate limit 1 000 calls/min per tenant, retry up to 3 attempts with exponential backoff, token refresh on 401.  
  - **Exception Flow**: OAuth token expired → automatic refresh; platform API down → queue for retry; quota exceeded → HTTP 429 with “Rate limit exceeded”.

### 🔹 Module: AI Pricing Engine

- **FR-3.0: Automated Price Adjustment**  
  - **Description**: System fetches competitor prices and demand signals every 5 min, applies tenant‑defined pricing rules, calculates new price, and writes to product catalog.  
  - **Metrics/Thresholds**: Pricing calculation < 100 ms per SKU, update frequency 5 min, price delta capped at ±20 % of current price, rule evaluation < 50 ms per cycle.  
  - **Exception Flow**: Competitor data unavailable → fallback to static rule; pricing rule validation failure → campaign paused, notification sent.

- **FR-3.1: Pricing Rule Management**  
  - **Description**: Tenants create/edit pricing rules (competitor monitoring, demand elasticity, discount thresholds). Rules are validated against schema before activation.  
  - **Metrics/Thresholds**: Rule creation < 2 s, rule edit < 1 s, rule evaluation < 50 ms, max 100 rules per tenant.  
  - **Exception Flow**: Invalid rule syntax → HTTP 400 with validation errors. Rule exceeds tenant limit → HTTP 409.

### 🔹 Module: Real‑Time Inventory Sync

- **FR-4.0: Inventory Synchronization Service**  
  - **Description**: Pulls inventory counts from POS, ERP, and sales channels every 30 s, reconciles with internal catalog, writes updates, and triggers alerts on anomalies.  
  - **Metrics/Thresholds**: Sync latency < 30 s, update throughput 10 k SKUs/min, inventory negative detection < 1 s, database write latency < 50 ms.  
  - **Exception Flow**: Network timeout → retry up to 5×; inventory discrepancy → alert admin, freeze sales for affected SKU.

- **FR-4.1: Manual Inventory Adjustment & Reconciliation**  
  - **Description**: Allows bulk adjustments via CSV upload or UI, validates against current stock, generates reconciliation report.  
  - **Metrics/Thresholds**: Adjustment latency < 1 s, CSV processing 5 k rows < 2 s, report generation < 5 s.  
  - **Exception Flow**: Adjustment leads to negative stock → operation blocked, error logged.

### 🔹 Module: Analytics & KPI Dashboard

- **FR-5.0: Real‑Time Dashboard Rendering**  
  - **Description**: Consolidated view of sales volume, pricing impact, ad performance, inventory health. Data refreshed every 60 s, charts rendered client‑side.  
  - **Metrics/Thresholds**: Dashboard load < 3 s, data refresh interval 60 s, chart rendering < 500 ms, max 10 concurrent dashboard sessions per tenant.  
  - **Exception Flow**: Data source unreachable → stale data displayed with banner warning; user can trigger manual refresh.

### 🔹 Module: Multi‑Tenancy & Data Isolation

- **FR-6.0: Tenant Provisioning & Schema Isolation**  
  - **Description**: Each shop becomes a tenant with separate PostgreSQL schema, Redis namespace, and storage bucket. Tenant creation includes resource quotas (CPU, memory, storage).  
  - **Metrics/Thresholds**: Tenant creation < 5 s, schema creation < 1 s, query latency per tenant < 100 ms, storage quota 5 GB per tenant.  
  - **Exception Flow**: Quota exceeded → HTTP 403 with “Tenant resource limit reached”. Cross‑tenant query attempt → HTTP 403.

- **FR-6.1: Tenant‑Specific RBAC & Permission Propagation**  
  - **Description**: Roles and permissions are scoped to tenant; changes propagate instantly via cache invalidation.  
  - **Metrics/Thresholds**: Permission check < 5 ms, role change propagation < 2 s.  
  - **Exception Flow**: Permission escalation attempt → audit log, HTTP 403.

### 🔹 Module: CI/CD & Deployment Automation

- **FR-7.0: Automated Build & Test Pipeline**  
  - **Description**: Source code triggers GitHub Actions → Docker image build → unit/integration tests → security scans → artifact push to Artifact Registry.  
  - **Metrics/Thresholds**: Build time < 10 min, test coverage > 90 %, security scan completion < 15 min, pipeline failure notification within 5 min.  
  - **Exception Flow**: Test failure → pipeline aborts, PR blocked; security vulnerability → automatic rollback to previous stable image.

- **FR-7.1: Containerization & Kubernetes Orchestration**  
  - **Description**: Services packaged in Docker images (< 500 MB). Helm charts define deployments, services, ingress. Horizontal pod autoscaler scales based on CPU > 70 % for 5 min.  
  - **Metrics/Thresholds**: Image size < 500 MB, pod startup < 30 s, auto‑scale min 2 pods, max 10 pods, rollout duration < 5 min, rollback < 2 min.  
  - **Exception Flow**: Pod health check failure → restart; if 3 consecutive failures → replace pod.

- **FR-7.2: Monitoring, Alerting & Observability**  
  - **Description**: Prometheus collects metrics (CPU, memory, request latency). Grafana dashboards visualize. Alertmanager sends alerts to Slack/PagerDuty. Immutable audit logs stored in Cloud Storage with AES‑256.  
  - **Metrics/Thresholds**: Metric collection latency < 1 s, alert response time < 2 min, log retention 365 days, log write latency < 2 s.  
  - **Exception Flow**: Alert threshold breach → notification; log write failure → retry 3×; after failure, critical actions logged locally.

- **FR-7.3: Security Hardening & API Gateway**  
  - **Description**: API Gateway (Envoy) enforces mutual TLS, JWT validation, rate limiting (1 000 req/min per tenant), WAF rules. Secrets managed via Secret Manager with 30‑day rotation.  
  - **Metrics/Thresholds**: Rate‑limit enforcement < 10 ms, secret rotation interval 30 days, vulnerability scan < 15 min.  
  - **Exception Flow**: Rate limit breach → HTTP 429; invalid JWT → HTTP 401; WAF block → HTTP 403.

### 🔹 Module: Audit & Compliance

- **FR-8.0: Immutable Audit Logging**  
  - **Description**: All critical actions (user creation, price rule changes, ad schedule updates, tenant provisioning) are logged to append‑only storage with SHA‑256 hash chain. Logs retained 365 days, encrypted at rest (AES‑256).  
  - **Metrics/Thresholds**: Log write latency < 2 s, log size per action < 5 KB, hash verification on read < 100 ms.  
  - **Exception Flow**: Log storage failure → local buffer with periodic sync; after recovery, replay logs.

## 📊 Edge‑Case & State Lifecycle Mapping

Core business entities and their strict state‑machine definitions:

| Entity | States | Valid Transitions | Exception Handling |
|--------|--------|-------------------|--------------------|
| **Shop (Tenant)** | `Created` → `Active` → `Suspended` → `Deleted` | `Created` → `Active` (owner verification) <br> `Active` → `Suspended` (quota breach, unpaid) <br> `Suspended` → `Active` (remediation) <br> Any → `Deleted` (explicit delete) | `Suspended` → `Active` requires admin approval; transition logs audit entry. |
| **Product** | `Draft` → `Active` → `Discontinued` → `Archived` | `Draft` → `Active` (approval) <br> `Active` → `Discontinued` (manual) <br> `Discontinued` → `Archived` (30 d inactivity) <br> `Active` → `Draft` (edit) | Invalid price range → block transition to `Active`, return error. |
| **Inventory** | `InSync` → `OutOfSync` → `Updating` → `Error` | `InSync` → `Updating` (sync start) <br> `Updating` → `InSync` (success) <br> `Updating` → `OutOfSync` (partial failure) <br> `OutOfSync` → `Error` (manual intervention) | `Error` → `InSync` after admin correction; logs generated. |
| **PricingRule** | `Defined` → `Active` → `Paused` → `Expired` | `Defined` → `Active` (validation pass) <br> `Active` → `Paused` (admin) <br> `Active` → `Expired` (time‑based) <br> `Paused` → `Active` (resume) | Validation failure → rule stays `Defined`, notification sent. |
| **AdCampaign** | `Draft` → `Scheduled` → `Running` → `Completed` → `Cancelled` | `Draft` → `Scheduled` (schedule time) <br> `Scheduled` → `Running` (start) <br> `Running` → `Completed` (end) <br> Any → `Cancelled` (manual) | Platform API failure during `Running` → transition to `Error` (new state) and retry. |
| **UserAccount** | `Invited` → `Active` → `Suspended` → `Deactivated` | `Invited` → `Active` (email verification) <br> `Active` → `Suspended` (MFA failure >5) <br> `Suspended` → `Active` (remediation) <br> Any → `Deactivated` (delete) | `Suspended` → `Active` requires password reset and re‑MFA. |
| **Session** | `Valid` → `Expired` → `Revoked` | `Valid` → `Expired` (idle >15 min) <br> `Valid` → `Revoked` (logout / admin) | `Revoked` session token rejected with HTTP 401. |

All transitions are logged in the audit trail with timestamps and user IDs.

## 🛡️ 3. Non‑Functional Requirements (NFR)

- **NFR‑1: Performance & Scalability**  
  - **Throughput**: API must sustain 10 000 requests per second (RPS) with response time ≤ 200 ms (95th percentile).  
  - **Concurrent Users**: Support up to 5 000 concurrent tenant users.  
  - **Database**: PostgreSQL read latency ≤ 50 ms, write latency ≤ 100 ms.  
  - **Auto‑Scaling**: Horizontal pod autoscaler scales from 2 to 10 instances based on CPU > 70 % for 5 min; database read replicas scale to 3.  
  - **Availability**: 99.99 % SLA (annual downtime ≤ 52.56 minutes).  

- **NFR‑2: Security & Compliance**  
  - **Authentication**: JWT (RS256) with 15‑min access token, 24‑h refresh token, mandatory TOTP MFA.  
  - **Authorization**: Role‑based access control per tenant, OAuth2 scopes, API Gateway rate limiting 1 000 req/min per tenant.  
  - **Password Policy**: Minimum 12 characters, upper/lower/digit/special, history 5, Argon2id hashing (64 MiB, 3 iter).  
  - **Encryption**: TLS 1.3 for all in‑transit traffic, AES‑256 at rest, secret rotation every 30 days.  
  - **Audit & Logging**: Append‑only immutable logs, SHA‑256 hash chain, retention 365 days, GDPR‑compliant data handling.  
  - **Vulnerability Management**: Weekly OWASP ZAP scans, automated remediation within 48 h.  

- **NFR‑3: Reliability & Availability**  
  - **Uptime**: 99.99 % monthly availability, RTO (Recovery Time Objective) ≤ 30 minutes, RPO (Recovery Point Objective) ≤ 5 minutes.  
  - **Failover**: Multi‑AZ deployment across 2 Google Cloud regions, automatic fail‑over on pod or database node loss.  
  - **Backup**: Daily full backups, point‑in‑time recovery to last 5 minutes, stored in cross‑region bucket.  
  - **Disaster Recovery**: Quarterly DR drills, documented runbooks, automated failover scripts.
