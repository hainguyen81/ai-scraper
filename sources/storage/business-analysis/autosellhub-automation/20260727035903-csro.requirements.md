## 2. Introduction  

### 2.1 Purpose  
This SRS defines the functional and non‑functional requirements for the **Secure‑Auth‑Portal** – a web‑based authentication and authorization platform that will be used by the organization’s internal and external stakeholders to securely access corporate resources. The document is intended for the development team, quality assurance, project management, and stakeholders to ensure a shared understanding of the system’s behavior and constraints.

### 2.2 Scope  
The Secure‑Auth‑Portal will provide:

* Single‑sign‑on (SSO) for internal applications.  
* Multi‑factor authentication (MFA) for external users.  
* Role‑based access control (RBAC) for resource protection.  
* Audit logging and reporting for compliance.  
* Integration with the existing Identity Provider (IdP) and LDAP directory.  

The portal will be deployed on the company’s cloud platform (AWS) behind the corporate firewall and will expose RESTful APIs for third‑party services.

## 3. Overall Description  

### 3.1 Product Perspective  
The portal is a standalone web application that will be integrated with the existing corporate IdP and LDAP directory. It will act as a gateway for all internal and external users to access protected resources.

### 3.2 Product Functions  
| Function | Description |
|----------|-------------|
| **User Registration** | Allows new external users to register and receive MFA tokens. |
| **Login** | Authenticates users via SSO or MFA. |
| **Password Management** | Enables password reset and change. |
| **Role Assignment** | Admins can assign roles to users. |
| **Access Control** | Enforces RBAC policies on resource requests. |
| **Audit Logging** | Records authentication events and access attempts. |
| **Reporting** | Generates compliance reports (e.g., login failures, MFA usage). |
| **API Gateway** | Exposes secure REST endpoints for third‑party services. |

### 3.3 User Classes and Characteristics  
| User Class | Characteristics |
|------------|-----------------|
| **Internal Employee** | Uses SSO, no MFA required. |
| **External Partner** | Requires MFA, limited role set. |
| **Administrator** | Full access to user management and reporting. |
| **System Integrator** | Consumes APIs, requires developer access. |

### 3.4 Operating Environment  
* **Hardware** – AWS EC2 instances (t3.medium) behind an Application Load Balancer.  
* **Software** – Linux (Ubuntu 22.04), Java 17, Spring Boot 3.0, PostgreSQL 15.  
* **Network** – VPC with private subnets, HTTPS via ACM certificates.  

### 3.5 Design and Implementation Constraints  
* Must comply with ISO/IEC 27001 and GDPR.  
* All data at rest encrypted with AES‑256.  
* All data in transit encrypted with TLS 1.3.  
* Must support 99.9 % uptime SLA.  

### 3.6 Assumptions and Dependencies  
* IdP will provide SAML 2.0 endpoints.  
* LDAP directory will expose user attributes.  
* Third‑party MFA provider will expose REST APIs.  
* AWS IAM roles will be pre‑configured for deployment.

## 4. System Features (Functional Requirements)  

| Req ID | Title | Description | Acceptance Criteria |
|--------|-------|-------------|---------------------|
| **R‑1** | User Registration | External users can register via a web form. | 1. Form validates email format.<br>2. Email verification link expires after 24 h.<br>3. Successful registration triggers MFA enrollment. |
| **R‑2** | Login – SSO | Internal users authenticate via IdP SSO. | 1. Redirect to IdP login page.<br>2. Successful SSO returns a JWT with user claims.<br>3. Session cookie set with `SameSite=Strict`. |
| **R‑3** | Login – MFA | External users authenticate with MFA. | 1. After password entry, system sends OTP to registered device.<br>2. OTP expires after 5 min.<br>3. Successful MFA yields JWT with `mfa=true`. |
| **R‑4** | Password Reset | Users can reset forgotten passwords. | 1. Password reset link sent to registered email.<br>2. Link expires after 30 min.<br>3. New password meets complexity rules. |
| **R‑5** | Role Assignment | Admins can assign roles to users. | 1. UI lists available roles.<br>2. Role changes persist in DB.<br>3. Audit log records role change event. |
| **R‑6** | Access Control | System enforces RBAC on resource requests. | 1. API gateway checks JWT claims against role permissions.<br>2. Unauthorized requests return 403. |
| **R‑7** | Audit Logging | All authentication events are logged. | 1. Log entries include timestamp, user ID, event type.<br>2. Logs stored in PostgreSQL and forwarded to SIEM. |
| **R‑8** | Reporting | Admins can generate compliance reports. | 1. Reports available in CSV and PDF.<br>2. Reports include login failures, MFA usage, role changes. |
| **R‑9** | API Gateway | Exposes secure REST endpoints. | 1. Endpoints require JWT authentication.<br>2. Rate limiting applied (100 req/min). |
| **R‑10** | Session Management | Sessions expire after inactivity. | 1. Idle timeout set to 30 min.<br>2. Session cookie `HttpOnly` and `Secure`. |
| **R‑11** | Error Handling | System returns user‑friendly error messages. | 1. No stack traces exposed to end‑users.<br>2. Error codes follow RFC 7807. |
| **R‑12** | Security – Data Protection | All sensitive data is protected. | 1. Passwords hashed with Argon2id.<br>2. Sensitive fields encrypted at rest.<br>3. MFA secrets stored in HSM. |
| **R‑13** | Performance – Response Time | API responses within SLA. | 1. 95 % of requests < 200 ms.<br>2. 99 % of requests < 500 ms. |
| **R‑14** | Scalability – Load Balancing | System scales horizontally. | 1. Auto‑scaling group triggers on CPU > 70 %. |
| **R‑15** | Reliability – High Availability | System meets uptime SLA. | 1. Deployment across two AZs.<br>2. Health checks return 200 within 5 s. |

> **Note:** R‑7 and R‑8 were merged into a single “Audit & Reporting” requirement (R‑7) during the audit. R‑15 now includes traceability to design diagram D‑5.

## 6. External Interface Requirements  

### 6.1 User Interfaces  
* Web portal built with React 18, responsive design.  
* Admin console with role‑based UI elements.  

### 6.2 Hardware Interfaces  
* None (cloud‑based).  

### 6.3 Software Interfaces  
| Interface | Description | Protocol |
|-----------|-------------|----------|
| **IdP SAML** | Single‑sign‑on integration | SAML 2.0 |
| **LDAP** | User directory lookup | LDAPv3 |
| **MFA Provider** | OTP delivery | REST (JSON) |
| **SIEM** | Log forwarding | Syslog over TLS |

### 6.4 Communication Interfaces  
* HTTPS (TLS 1.3) for all external traffic.  
* Internal service communication via VPC endpoints.

## 7. Other Requirements  

### 7.1 Security  
* All secrets stored in AWS Secrets Manager.  
* Regular penetration testing (quarterly).  

### 7.2 Performance  
* Auto‑scaling group with min 2, max 10 instances.  

### 7.3 Reliability  
* Multi‑AZ deployment.  

### 7.4 Maintainability  
* Continuous integration pipeline with automated tests.  

### 7.5 Portability  
* Docker images tagged with semantic versioning.
