## 1. Introduction  

### 1.1 Purpose  
The purpose of this document is to capture the complete set of functional and non‑functional requirements for the **Triple‑Check Protocol** application. It serves as the single source of truth for all stakeholders, ensuring alignment between product ideas, design, development, testing, and deployment activities.  

### 1.2 Scope  
This SRS covers the end‑to‑end behavior of the application, including user authentication, API exposure, data persistence, logging, monitoring, and deployment. It does **not** include detailed implementation code, third‑party library specifications, or operational run‑books.  

### 1.3 Business Context  
The application is a modern web‑service platform that provides core business functions such as user management, product catalog handling, and order processing. It must comply with internal coding standards, security best practices, and documentation policies as defined in the **Triple‑Check Protocol** audit framework.

## 2. Overall Description  

### 2.1 Product Perspective  
The system is composed of three primary layers:  

1. **Presentation Layer** – Single‑page application (SPA) built with a modern front‑end framework.  
2. **Application Layer** – Node.js micro‑services exposing RESTful APIs.  
3. **Data Layer** – PostgreSQL database accessed via an ORM.  

### 2.2 System Architecture  
The architecture follows a **micro‑services** pattern. Key components are:  

- **Auth Service** – Handles JWT issuance, validation, and refresh.  
- **User Service** – Manages user accounts and profiles.  
- **Product Service** – Exposes product catalog operations.  
- **Order Service** – Processes orders and integrates with payment gateways.  

All services communicate over HTTPS. The system diagram is referenced in `docs/blueprint.md` with a version comment (`<!-- Version: 1.0 -->`).  

### 2.3 Key Features  

| Feature | Description |
|---------|-------------|
| **User Authentication** | JWT‑based auth with token refresh before expiration. |
| **API Consistency** | All endpoints use **kebab‑case** (e.g., `/user-profile`, `/product-item`). |
| **Error Logging** | Full stack traces logged via `console.error(err.stack)`. |
| **Secure Configuration** | Database connection string stored in `DB_CONNECTION_STRING` environment variable. |
| **Code Quality** | No unused imports; duplicate CSS rules removed. |
| **Documentation** | Contributing guidelines added to `README.md`. |

## 3. Functional Requirements  

### 3.1 Authentication & Session Management  
- **FR‑001**: Issue a JWT upon successful login (valid for 30 minutes).  
- **FR‑002**: Automatically refresh the JWT **before** expiration; on refresh, return a new token without requiring re‑authentication.  
- **FR‑003**: Reject any request with an invalid or expired token (HTTP 401).  

### 3.2 API Endpoint Conventions  
- **FR‑004**: All route definitions must use **kebab‑case** naming (e.g., `GET /order-history`).  
- **FR‑005**: Route paths must be documented in `src/api/routes.js` with a leading comment indicating the HTTP method and purpose.  

### 3.3 User Management  
- **FR‑006**: Create, read, update, and delete user profiles.  
- **FR‑007**: User data must be validated against a schema (email format, required fields).  

### 3.4 Product Catalog  
- **FR‑008**: Retrieve list of products (`GET /products`).  
- **FR‑009**: Retrieve a single product by identifier (`GET /product/{id}`).  
- **FR‑010**: Add new product (`POST /product`).  

### 3.5 Order Processing  
- **FR‑011**: Create a new order (`POST /order`).  
- **FR‑012**: Retrieve order status (`GET /order/{id}`).

## 5. Architecture & Design  

### 5.1 Technology Stack  

| Layer | Technology |
|-------|------------|
| **Front‑End** | React 18 + TypeScript |
| **Back‑End** | Node.js 20 + Express |
| **Database** | PostgreSQL 15 (via TypeORM) |
| **Auth** | JWT (HS256) with refresh token store |
| **CI/CD** | GitHub Actions |
| **Monitoring** | Winston logger + Prometheus metrics |

### 5.2 Data Flow  

1. Client sends authenticated request → **Auth Middleware** validates JWT.  
2. Request routed to appropriate service (User, Product, Order).  
3. Service interacts with **Database** via ORM.  
4. Service logs business events (info) and errors (error + stack).  
5. Response returned to client; token refreshed if nearing expiry.  

### 5.3 Security Controls  

- **Transport Layer**: HTTPS with TLS 1.3.  
- **Authentication**: JWT with short‑lived access tokens + refresh token.  
- **Authorization**: Role‑based access control (RBAC) using scopes.  
- **Input Validation**: Joi / class‑validator on all request bodies.  
- **Output Encoding**: Automatic escaping in the front‑end.

## 6. API Specifications  

All endpoints are versioned under `/api/v1`. Example:  

```http
GET /api/v1/products HTTP/1.1
Host: api.example.com
Authorization: Bearer <access_token>
```

### 6.1 Authentication Endpoint  

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/api/v1/auth/login` | Exchange credentials for JWT access/refresh tokens. |
| `POST` | `/api/v1/auth/refresh` | Obtain a new access token using a valid refresh token. |

### 6.2 User Endpoints  

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/api/v1/users/me` | Retrieve current user profile. |
| `PUT` | `/api/v1/users/me` | Update current user profile. |
| `DELETE` | `/api/v1/users/me` | Deactivate current user. |

### 6.3 Product Endpoints  

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/api/v1/products` | List all products (paginated). |
| `GET` | `/api/v1/products/{id}` | Retrieve a single product. |
| `POST` | `/api/v1/products` | Create a new product (admin only). |
| `PATCH` | `/api/v1/products/{id}` | Update product details (admin only). |
| `DELETE` | `/api/v1/products/{id}` | Remove product (admin only). |

### 6.4 Order Endpoints  

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/api/v1/orders` | Create a new order (authenticated user). |
| `GET` | `/api/v1/orders/{id}` | Retrieve order status (owner or admin). |
| `GET` | `/api/v1/orders` | List orders for the authenticated user (paginated). |

**Note:** All route definitions in `src/api/routes.js` must be **kebab‑case** (e.g., `order-history`).

## 7. Data Management  

### 7.1 Database Schema  

- **users** – id, email, passwordHash, role, createdAt, updatedAt.  
- **products** – id, name, description, price, stock, createdAt, updatedAt.  
- **orders** – id, userId, status, total, createdAt, updatedAt.  
- **order_items** – id, orderId, productId, quantity, price.  

### 7.2 Connection Configuration  

The database connection string must be supplied via the environment variable `DB_CONNECTION_STRING`. Example:  

```bash
DB_CONNECTION_STRING=postgresql://user:pass@host:5432/dbname
```  

The configuration file `config/db.js` should read this variable and fall back to a local default only for development.

## 8. Testing & Quality Assurance  

### 8.1 Test Coverage  

- **Product Model** (`src/models/productModel.js`) – Target **≥ 70 %** line coverage.  
- Additional unit tests required for `save()` and `findById()` methods.  

### 8.2 Test Strategy  

| Test Type | Tool | Coverage Goal |
|-----------|------|---------------|
| **Unit** | Jest | 80 % of service layer |
| **Integration** | Supertest | End‑to‑end API behavior |
| **Security** | OWASP ZAP | Identify common vulnerabilities |
| **Performance** | k6 | Latency < 200 ms for CRUD ops |

### 8.3 CI/CD Pipeline  

- **Lint** – ESLint (enforce code style).  
- **Format** – Prettier (no trailing whitespace).  
- **Test** – Run Jest + Supertest suite; fail if coverage < 70 % for productModel.  
- **Security Scan** – Snyk for dependency vulnerabilities.

## 9. Deployment & Operations  

### 9.1 Deployment Targets  

- **Development** – Docker containers with local PostgreSQL.  
- **Staging** – Kubernetes cluster with external PostgreSQL.  
- **Production** – Managed Kubernetes (EKS/GKE) with encrypted storage.  

### 9.2 Release Process  

1. **Version Tag** – All diagrams and documentation include `<!-- Version: X.Y -->`.  
2. **Branch Strategy** – `main` (production), `develop` (integration), feature branches.  
3. **Automated Tests** – Must pass before merge to `develop`.  
4. **Artifact** – Container images built with multi‑stage Docker builds; pushed to container registry.  

### 9.3 Monitoring & Logging  

- **Application Logs** – Winston logger writes to JSON files; errors include stack traces.  
- **Metrics** – Prometheus exporters for request latency, error rates, DB connections.  
- **Alerts** – PagerDuty integration for critical errors (e.g., auth failures, DB downtime).
